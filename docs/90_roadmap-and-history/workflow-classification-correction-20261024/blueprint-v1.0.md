# 工作流分类直选与组装核验修正蓝图 v1.0

日期：2026-10-24。状态：待用户核验，尚未实施产品修正。

本次已完成源码比对、当前正式配置读取和本地诊断复现；仅新增本蓝图及审计材料，没有修改产品代码、正式配置、SCF 部署或发布状态。

## 一、结论与责任边界

本轮分类填写界面确实偏离了用户原始要求。用户要求的是：在工作台设计端，以四级分类选框定义分类组的候选范围；实际填写工作流时，沿用原先“类型”单一下拉框，将最终可选分类按“代号（名称）”直接列出。

我在上一版蓝图 WF-GROUP-03 中自行扩展出了“运行器使用四级联动选择”，随后按这个解释实现了 `WorkflowGroupCategoryInput`。这是需求解释和设计上的偏离。新组件还漏用了原有 select 样式，进一步造成截图中的视觉退化。它们都不是分类组算法所必需，也不是用户本地缓存问题。

修正原则：**设计端定义范围，填写端直接选最终分类，组装按完整所选路径绑定；工作流配置对全部可达候选逐一检查最终写入字段和格式。** 不要求组内所有分类的全部字段定义相同。

本蓝图替代旧蓝图 WF-GROUP-03 的“运行器四级联动”条款，并纠正旧实现把共同字段集合当作部分绑定准入条件的行为。旧蓝图作为历史副本保留。

## 三、自检发现

### AUDIT-01：实际填写端被替换成了分类树浏览器——确认偏离

`V3WorkflowRunner.tsx` 的 c15 分类控件分支接入 `WorkflowGroupCategoryInput.tsx`。后者逐级生成 Class、Kind、SKind、SKind2，使用完整路径作每级选项文案，还增加了“使用当前分类本身”和“已选择”说明。

用当前正式配置中的 `v3-isg_ngf_wtb` 生成组件标记，确认会出现 **4 个 select，4 个都没有原先的 select 样式 class**，与截图一致。即使 Class／Kind／SKind 已被组范围固定，仍然重复展示这些层级。

原先自然水域工作流的实际填写组件则是一个类型下拉框，应用原有圆角、边框、间距和字号，直接显示终点类型选项。

### AUDIT-02：字段建议集合被用于实际绑定准入——确认存在误拦截

`workflowOutputFields()` 目前取所有候选字段的交集，并要求 type、cardinality、coordinateFormat、format、reference、valueSchema 等部分定义完全相等。该集合用于组装目标建议，还被以下入口用作准入条件：

- 预填字段并同时建立输出组装；
- 旧兼容字段导入的同时绑定；
- 绘制坐标／高度返回绑定；
- 显式编辑回填映射。

这使“提示哪些字段较通用”和“某个实际写入是否合法”混在一起。核心维护文档已经写明共同字段只用于编辑建议，实际实现没有始终遵守。

本地受控样例：候选 A 的 `AuditValue` 是普通文本，候选 B 的同名字段是外部链接文本；组装统一写入合法的 `https://example.org/item`。现有工作流核验通过，两个实际输出记录均通过现有记录核验，但该字段被共同字段集合排除，使使用这个集合的同时绑定入口拒绝它。不能因字段定义的 format 不同就否定满足双方约束的实际写入。

### AUDIT-03：逐候选核验已存在，但必填供值覆盖仍有缺口——确认可复现

当前 `runtime.ts` 已逐候选调用输出检查和 `validateWorkflowWrites()`。因此不能概括为“完全没有检查其他分类”，也不需要推翻既有候选解析器。

但现有配置预检主要检查已写入的组装行，没有完整检查每个候选的必填字段是否有供值来源。

本地受控样例：给候选 A 增加没有默认值的必填字段 `RequiredOnlyA`，工作流没有任何供值行；工作流配置核验仍为通过，而 A 的实际输出提交核验报“RequiredOnlyA 为必填项”。这类静态可确定的问题应提前阻断工作流保存／发布。

以上两个字段样例为隔离诊断夹具，并非声称线上当前所有工作流已有这些数据错误。

### AUDIT-04：编辑端可选范围与最终编辑范围未完整对齐——确认调用缺口

`NativeWorkflowEditPanel` 也复用新分类组件，但传入的是整个 output，没有将编辑计划经过 `editor.scope` 筛选的候选集合传入选择器。保存端仍检查该范围，因而在“编辑范围小于整组范围”的配置下，可能出现界面可选、保存时才拒绝的情况。

修正时新建、试运行和编辑应复用同一显示组件，但分别接收自己真正有权选择的候选，不能编辑时扩大范围。

### AUDIT-05：原有标题含固定范围说明——需随实际候选核对

迁移保留了系统分类控件原 ID、位置和 label，因此截图仍显示“类型（Kind=NGF, SKind=WTB）”。对当前这个水域工作流，该固定范围说明本身仍成立；不能把它一律认定为错误。

但用户后续扩大分类组后，不能继续显示已经不成立的系统范围提示。应区分用户自定义标题和系统派生说明，不能靠批量字符串替换改写用户标题，也不能用过期的标题文字决定候选范围。

### AUDIT-06：验收覆盖了新实现，却没有覆盖原始交互要求——确认测试缺口

已有浏览器验收覆盖了分类组设计、指定方式切换、折叠、核验、导出和保存；内核测试覆盖精确父节点、候选资格、导入和多输出身份。

但缺少“实际填写端依然只有一个类型下拉框、末端层级混合仍平铺、外观保持一致”的验收。原有测试通过不能证明该交互符合用户要求。本次验收必须从用户预期写断言，不能沿用四级控件作为正确答案。

## 五、SELECT-01：恢复实际填写端的直接选择

### 5.1 两端明确分工

**工作台设计端：** 分类组内每一行仍使用四级分类选框定义目标，选择“指定分类本身”或“指定分类下所有末端分类”；整组在这些行下设置固定绘制类型。

**实际填写端／试运行／工作流式编辑：** 每个需要用户选择分类的输出只显示一个原风格的类型下拉框。候选集为已解析的最终合格分类，不要求用户重新沿 Class 树展开。

例如同组末端分别停在 Kind、SKind、SKind2，填写端仍直接列出三种终点：

```text
类型 *
[请选择类型                 ▼]
  A（某种类型）
  B（另一类型）
  C（第三种类型）
```

选项主文案取该真实节点最后一层的分类代号及其名称，不默认显示完整祖先路径，不追加 Kind／SKind 层级标签。精确 self 目标同样直接作为一项，不再额外点击“使用当前分类本身”。

### 5.2 显示、值与顺序

- 复用原有工作流 select 样式和外围表单布局，保持字号、宽度、圆角、边框、内边距、焦点和错误态；不另造一套灰色原生下拉框。
- 展示为 `最后一级代号（该级名称）`；缺名称时回退代号。采用现有分类名称解析及语言回退规则，不从标题中的 `Kind=…` 解析业务范围。
- 内部 option 身份仍使用完整 ClassificationPath 的稳定键，不能只保存末级代号。同名、同代号的不同完整路径不得互相覆盖。
- 如果不同路径的“代号（名称）”完全重名，仅对这些冲突项增加最短的父级区分提示；普通选项不膨胀成完整路径。
- 按既有配置声明顺序稳定展示，去重后保留首个出现位置；不擅自按代码重排原先选项。
- 多候选时保留“请选择”空状态，不默认选择第一项。只有一个有效候选时沿用原先自动确定行为，不要求多余的层级确认。
- 无有效候选时显示明确错误并阻断继续；不从组外找一个可用类型填入。

### 5.3 最终分类绑定

选项携带完整路径。进入绘制和最终组装时仍检查成员资格、固定 Type、几何启用和部件政策，然后由当前所选路径提供 Class、Kind、SKind、SKind2 及各输出系统 token。

从 SKind2 末端切换到 Kind 末端时，旧的 SKind／SKind2 不得残留；从一个 Class 切换到另一个 Class 时，同样完整替换路径。Label 文案、控件显示值和记录身份必须指向同一个候选。

分类组或分类树更新使当前选择失效时，保留输入和几何草稿保护，显示失效原因并要求重选；不静默改为首项。

编辑端候选额外与编辑计划的 `editor.scope` 及既有编辑资格求交集，回填原记录完整分类。不能选择最终必定无法保存的组外／编辑范围外分类。

## 六、WRITE-01：按最终组装对全部候选检查合法性

### 6.1 核验对象

检查的是每个可达候选实际会收到的字段和值约束，不是比较全部字段定义是否一模一样。

```text
解析最终候选
→ 对每个候选建立当前完整分类的系统值
→ 保留原输出顺序及跨输出依赖
→ 分析本候选可达的组装行、绘制返回绑定和默认供值
→ 按该候选有效字段定义检查目标、类型、数量、格式、约束和必填覆盖
→ 汇总问题并定位到分类、输出、来源行
```

分类的可选字段不同，但本工作流未写入它们，且没有造成该分类必填缺失时，不因此阻断工作流。

### 6.2 字段建议与绑定检查分离

- 将共同字段建议与真实写入兼容性检查拆成独立职责。共同字段可优先提示，但不再作为唯一准入集合。
- 目标字段提示可以展示候选字段并注明支持范围；手工输入和预填同时绑定必须调用与保存相同的兼容性检查。
- 无条件向所有候选写入的字段，须对所有可达候选合法。只在部分候选存在的字段，只有其执行条件可以证明排除了不支持该字段的候选时才可通过。
- 不自动删候选以掩盖字段问题，不自动改字段类型，不把缺失字段悄悄写入扩展区。
- tags／extensions 继续使用现有契约允许的路径及自定义规则，不因“分类组”引入第二套任意路径放行逻辑。
- 同步修复预填同时绑定、绘制返回、显式编辑回填、输出组装提示和对应核验入口，避免只改一个 datalist。

### 6.3 逐候选的字段和值约束

至少覆盖：保存目标是否合法、单值／多值、基础类型、枚举保存值与实际值类型、坐标格式、valueSchema、引用格式及适用的字段 format。

兼容性由具体可产生的值决定，而不以定义 JSON 相等代替。例如合法 URL 可同时满足普通文本字段和链接字段；相反，同为 string 的日期字段和链接字段，也不能仅因基础类型相同就认定组装安全。

沿用受控表达式 AST 与有界条件分析，不执行任意脚本。恒定非法值、确定的类型／格式冲突、必然无法满足的结构约束报错；无法静态确定的动态结果给出明确警告，并在实际输入完成后严格检查实际记录。

### 6.4 必填供值与条件覆盖

对每个候选的必填字段，检查供值是否来自：系统生成、对应绘制返回、合法默认值、适用组装行，或既有其他明确供值机制。

- 能静态确定“必填且没有任何供值来源”时，必须报错，不能等真实提交才发现。
- 有组装行不等于一定有值；恒定空值、永不执行或已被条件排除的行不能算有效覆盖。
- 检查字段 requiredWhen、输出／页面／组装启用条件与控件供值的可达关系。可选输入无法保证动态必填时，应明确提示，并保留实际填写前后的检查。
- 条件超出可证明范围时，输出“无法静态确认”的具体原因，不能伪造通过证明或采用固定假值试填当作全覆盖。
- 可选空字符串、空白、null 的既有省略政策和合法 0／false 保留；不得顺带放宽必填检查。

### 6.5 三层核验保持一致

1. **工作流／整包配置核验：** 对所有可达候选做上面的静态检查。
2. **实际填写、绘制和再编辑：** 按最终所选分类、实际值执行同源记录核验，再允许本地保存／组装输出。
3. **SCF 入站、审核与发布：** 复用同源字段和值约束，防止手工修改记录绕过前端；普通记录资格仍不依赖某条工作流是否存在。

不把仅服务工作流设计的可证明性分析施加到所有已有正式记录上；历史记录的准入规则及 validateExistingData 等既有政策保持清晰。

### 6.6 报告展示

错误需同时定位 workflowId、outputId、组装行或绘制绑定、字段及受影响完整分类。相同原因可以按现有问题分组机制合并，展开查看具体分类，不能只显示第一类或把不同原因合并掉。

动态 ConnectL／Blacklist 警告继续遵守“静态未知提示、实际值严格核验”，不因本次修正而一律清除，也不据此强制改变已合法的道路组装。

## 七、契约、迁移与部署处理

本轮不新增配置结构或新的作者选项，按 **c15 修正**实施，不为恢复正确界面而另造 c16。配置修订继续使用 r，正式配置修订号只由用户后续发布分配。

- 当前 r14／c15 配置原件、散列及发布身份不由代码部署自动重写；不要求用户重新迁移分类组。
- c13 → c14 → c15 的既有相邻迁移继续保留；本次修正是运行器解释和核验行为修复，不借同版导入批量改写用户 label、页、槽位和组装。
- 系统控件继续绑定原 outputId，保留控件 ID、页内位置及已有自定义标题。新建／导入／读取工作流仍同步控件资格，多个候选才生成选择控件。
- 系统派生范围说明根据实际候选更新；固定祖先范围已不成立时不继续显示该系统说明。用户自行填写的标题原样保留。
- 不改缓存恢复约定，不强制清空浏览器、不静默恢复默认。旧草稿按当前既有检查点流程显式恢复，选择值仍用完整路径读取。
- 由于本次包含共享核验修复，实施时须由 Web 同源重建 Node 核验器并同步 Pipeline，更新受影响的 worker／dispatcher 部署包。其原因是核验实现修复，不是配置修订号变化。
- 核验器构建身份、缓存失效和历史 rulesVersion 兼容按既有发布协议配套更新并测试，不能仅替换包内文件却继续复用旧核验结果。
- 部署新核验器不重置正式配置激活时间、不自行修改生产环境变量。真实 SCF／登录／发布验证列为部署后验收，与本机测试分开记录。

### SELECT 测试

| 场景 | 必须观察到的结果 |
| --- | --- |
| 当前正式水域工作流 | 只有一个类型 select；候选代号（名称）、顺序和原风格正确，不再出现四级填写控件 |

### WRITE 测试

- 只增加未使用的可选字段，不应使原合法工作流失败。
- 定义存在差异但同一实际写入满足双方约束的样例，允许预填绑定并通过核验。
- 一个候选不支持无条件写入字段、枚举值越界、单多值不符、坐标格式／结构／链接日期格式冲突时，正确报错并定位该候选。
- 候选特定条件组装：能证明只在支持分类执行时通过；条件无法排除不兼容分类时不能漏检。
- 某候选必填字段没有供值、供值恒为空、条件覆盖不完整时，按静态可判定程度报错或明确警告；实际缺值始终阻断。
- 绘制返回、预填同时绑定、显式回填、手写组装使用同一准入逻辑，不出现一处可选另一处拒绝。
- 动态 JSON 的未知警告与实际合法／非法值分别测试，不能把警告等同于已确认合法。
- 前端核验与纯 Node／Pipeline 对同一夹具给出一致结果；伪造的组外分类仍被拒绝。
