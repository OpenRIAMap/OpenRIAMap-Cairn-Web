# V3 配置体系转正与正式配置发布蓝图 v0.1

日期：2026-10-17。状态：待用户审查，本次仅固化蓝图，没有修改主程序、旧版入口或线上配置。

基线代码：`b1c57bf`。保留既有修复蓝图、执行报告、默认配置和人工阅读手册，不覆盖历史副本。

## 1. 目标与实施边界

本轮将当前 Config Studio 对应的配置体系用于正式主地图，把当前主地图的 V1 配置、显示和交互保存在单独兼容页面；增加配置编辑分包与 Maintainers 专属发布链路，最后补齐多部件/内洞的界面限制。

| --- | --- | --- |
| MAIN-01 | 正式主地图使用 V3 | 首个正式版本为当前 r11/r7，此后读取通过 pipeline 发布的版本。 |

| BUNDLE-01 | 配置编辑按需分包 | Studio、Lab 及其工作流编辑页归入“配置编辑”分包，不再静态进入主地图首包。 |

本轮首先替换的是**配置的读取与发布体系**。不把正式要素数据文件批量改写成配置 JSON，不重发数据/媒体发布，不改变现有正式数据读取协议。

## 2. 已核实的当前状态

1. App 普通主地图仍渲染 `<MapContainer />`，没有传入 configRuntime；V3 原生路径主要由 Config Lab 注入。
2. App 同时在全局运行 ConfigBootstrap，后者读取 IndexedDB 选择并应用 application 设置。因此当前存在“部分应用设置来自本地 V3，而主显示仍走 V1”的混合边界，转正时必须一并清理。
3. `nativeConfigLabActive` 同时承担原生渲染环境判定、旧图层排除、按钮过滤旁路等职责。正式接入不能仅把它改名后照搬，尤其不能让正式主地图继续旁路按钮过滤。
4. ConfigStudio、ConfigLab、WorkflowStudioPage 当前由 App 静态导入；现有 featureModuleStore 只登记 measuring/review/legacy。已有 legacy 分包是旧铁路/地标能力，不是完整 V1 配置兼容应用。
5. Studio 整包下载当前要求输入大于现有版本的修订号；仍有 V1 重建及迁移阶段说明。需要替换为正式版本管理界面。
6. OAuth 现有链路识别登录用户；Team 权限由 SCF 的 GitHub App 侧解析。浏览器保存的角色或用户名不能作为发布授权依据。
7. 本地可见的 `pipeline-config-runtime-v31` 快照内配置导入器明确限制 contractRevision=3。该事实不能用于推断当前线上 SCF 部署版本；执行前必须查明实际部署与最新 pipeline 源码，再补齐 r11 支持。
8. 旧 relay resolver 仍有从 V1 worlds.json、Class 配置读取定义的路径。正式任务必须改为通过统一正式配置上下文解析，不能只改地图。
9. 现有审核 broker 有 staging 启用条件。配置发布能力需要明确自己的环境与能力开关，不得因删除“实验性”文案就自动绕过审核部署门。
10. 分类 allowMultipleParts 在原生工作流最终记录核验时生效；通用部件按钮与工作流添加部件按钮尚未完整联动，内洞操作又与部件操作共用部分锁，需要拆分。

主要取证位置：`src/App.tsx`、`src/configStudio/defaultConfigProvider.ts`、`ConfigBootstrap.tsx`、`ConfigStudio.tsx`、`ConfigLab.tsx`、`src/components/Map/MapContainer.tsx`、`src/store/featureModuleStore.ts`、`api/auth/github/*`、`api/review-control.mjs`、`scripts/relay/native-relay-config-resolver.mjs`、pipeline 的 config-package-import-runtime/team-authorizer。

- 后续通过稳定的活动发布索引发现新配置；主程序不再硬编码只能读取 r11-r7 文件名。
- 配置仍保存为可人工阅读的 UTF-8 JSON；发布索引、事务状态等元数据放在外层文件，不混入已有配置正文。

### 3.2 三种配置状态明确分开

| 状态 | 来源 | 影响范围 |
| --- | --- | --- |
| 正式发布配置 | pipeline 活动发布索引 + 对应不可变配置 | 正式主地图、测绘/编辑约束、审核新任务。 |
| 工作台已保存编辑版本 | 浏览器本地编辑存储 | 工作台及明确选择该版本的试运行。 |
| 未保存草稿 | 当前模块或 Class 树草稿 | 只在编辑状态内，不作为发布快照。 |

现有本地历史与草稿原样保留、迁移读取；不因转正清空 IndexedDB。主地图不自动把旧的 custom 活动选择提升为正式配置。用户要将本地版本用于正式运行，走核验后的发布流程。

工作台的“保存”明确为保存编辑版本；Lab 可继续运行当前本地版本，但显示其来源和版本身份。这里保留版本来源说明，清理的只是过时阶段说明。

### 3.3 主页面完整接线

将同一个已验证、已编译的正式配置快照传给渲染、信息卡、搜索/导航、主附属视角、图层按钮、测绘、工作流再编辑、审核前端上下文和世界/瓦片设置。

拆开“是否 V3 运行时”和“是否配置实验室”两个判断。正式主地图按新按钮规则过滤，禁用 V1 专属显示叠加，不能开启实验室绕过筛选的旁路。

主包只保留运行时所需的读取/解析/验证核心；不要通过 core 引用反向打包编辑器、预览器和 V1 生成器。需对 import 图和最终构建产物实际验证。

### 3.4 加载、缓存与会话

- 活动索引采用重新验证的缓存策略；不可变配置使用内容散列 URL，可长期缓存。
- 先检查字节摘要与结构/语义，再启用。损坏或不受支持的发布不会静默转回 V1。
- 已有浏览器会话只使用之前确认有效的正式版本；索引暂不可用时可显示版本与错误并使用已有可信副本。首次基线为已登记的 r11/r7。
- 出现新发布时提示刷新/重新加载；不在测绘、编辑或审核草稿中途替换配置对象。任务开始时保存其配置身份。
- 检查浏览器/PWA/缓存层，不让旧索引把过期文件误当成新活动版本。

## 4. V1-01：独立“旧渲染规则入口”

采用独立页面入口，建议路径 `/legacy-v1/`；不是主地图中的 V1/V3 即时切换。原 `config-lab&configMode=v1` 旧地址引导至此页面，避免遗留入口绕过分包边界。

### 4.2 冻结范围

冻结转正前的 V1 配置、渲染器、信息卡、搜索/导航表现、世界和按钮布局、测绘与 V1 工作流行为及专属样式。将冻结清单、基准 commit 与文件散列归档。

V1 页面独立初始化 application、图层状态、存储命名空间及样式。不能经过当前全局 V3 ConfigBootstrap；不能读取、写入正式 V3 的编辑版本选择。全页入口避免模块全局单例在同一进程里互相覆盖。

### 4.3 继续读取远端正式数据

保留当前正式数据读取协议，规则与功能解释使用冻结 V1 定义。按 V1 已登记的**完整分类路径和所需几何能力**筛选，不只检查 Class。

未知 Class、未知下级分类、无法由 V1 解释的新几何/必要结构：逐条跳过，不阻断整个数据集，不猜测映射到已知默认分类，不写回源记录。搜索、导航候选及测绘引用池也只纳入 V1 能合法解释的记录。

已知记录的新可选字段按既有兼容方式保留/忽略，不因多了一个无关字段就丢弃整条记录。真正损坏的已知记录进入局部诊断；未知和损坏分别计数，不弹成全局失败。

“V1 兼容”标签、版本号和可选的跳过计数保留。V1 不提供 V3 配置发布入口；既有功能入口只按冻结能力工作，不隐式改用 V3 采集规则。

## 5. BUNDLE-01：配置编辑分包

新登记独立的“配置编辑”功能包，包含 ConfigStudio、ConfigLab、WorkflowStudioPage 及其编辑器/预览/导入导出依赖。动态入口统一处理加载、错误和版本匹配，不让工作流编辑页成为漏掉的静态入口。

保留现有按需分包体验：首次确认启用、显示加载状态、取消/失败回到原页面；此前成功启用且版本匹配时自动加载。通过设置入口和直接 URL 进入都遵守同一边界。

“V1 兼容分包”与既有 legacy 铁路/地标扩展不是同一个 ID；不复用旧 legacy 存储键来误判已加载。

初始主地图不请求配置编辑分包或 V1 UI/测绘分包。浏览器只下载 JSON 运行时和必要运行核心，不因同目录或大范围 manualChunks 规则把整个编辑器重新拉入主包。

### 6.2 全局核验门

“整包下载/上传”默认不可点击。必须通过其左侧的全局核验，才允许打开总包窗口；模块单独核验结果不能解锁它。

核验必须绑定到当前完整内容指纹、基础正式版本和核验规则版本。配置内容、绑定来源、待核验数据上下文或基础正式版本改变后，相应结果失效。不能复用先前另一份配置的通过报告。

模块/树/工作流仍有未归并草稿时，提示先保存或放弃对应草稿，不偷偷忽略并下载旧版本，也不擅自丢弃草稿。全局核验针对确定的已保存编辑快照执行。

窗口含下载、上传入口及明确关闭按钮。关闭、取消 OAuth 或上传失败保持编辑内容。Lab 若保留总包导出/发布入口，复用相同核验门，不能成为旁路。

## 7. REV-01：自动修订号

- 删除整包导出窗口的数字输入框，改为只读的自动生成版本说明。
- contractRevision 是结构兼容版本，不随每次下载递增；revision 是包修订号。
- 本地下载按当前包、已知本地导出历史和最新已知正式版本自动分配更高 revision；成功生成后保存版本记录，取消窗口不产生空版本。
- 在线发布由服务端按正式版本高水位和提交候选自动分配/确认唯一修订号，不信任客户端自称的下一个版本。
- 离线导出号不代表占用了服务器发布号。若服务器正式版本已前进，自动形成新候选，展示最终修订和散列，重新核验后再确认上传，不暗中修改已确认快照。
- 同一次下载操作的重试复用该产物；同一发布幂等请求复用同一发布结果，不因网络重试重复递增。
- 并发或中止可能留下未启用号，保证单调与唯一，不以复用历史版本号追求无缺号。
- 外部旧包导入继续保留来源身份与历史，发布到当前应用时重新形成受控候选；不开放任意 packageId/projectId 指向其他项目。

本轮不为发布元数据改写 r11/r7 的冻结正文。新索引/发布凭证使用独立结构版本；确需扩展作者配置契约时，明确升级并保留 r11 导入，不通过篡改旧 r7 文件伪装首版。

## 8. AUTH-01：重新登录与 Maintainers 权限

### 8.1 交互

全局核验通过 → 打开“整包下载/上传” → 点击上传 → 再次启动 GitHub OAuth → 服务端确认身份与 Team → 打开发布确认页 → 再次确认核验 → 上传并发布。

再次登录使用本次独立 state/nonce，并绑定发布用途、当前包内容、基础正式版本与有效期；不能只读已有八小时会话就视为已完成本次确认。可用 GitHub 官方 account picker 请求明确选择身份；其可能复用已有 GitHub 会话，不承诺每次都强制重新输入密码。

### 8.2 授权规则

- 目标组织 OpenRIAMap，Team slug `cairn-maintainers`。
- 通过 GitHub App 在可信服务端查询实际 Team membership，要求 state=active；Team 内普通 member 和 maintainer 都属于该组，不把组名误解成只允许 GitHub Team 的 maintainer 子角色。
- 非成员、pending、查询失败、会话过期或无法核实均不放行；不能用前端缓存、静态用户名名单或用户自行提交的 approvedRole 替代。
- 提交核验与最后确认发布都检查权限；最终确认不因旧角色缓存未过期而忽略已撤销成员资格。
- OAuth 回调验证 state、来源窗口和短期凭证；最后请求包含服务端核验结果引用与防重放信息。浏览器不接触 GitHub 写 token、COS 密钥或 SCF worker 权限。
- 发布控制面不受待发布配置自身的 review.enabled、auth URL 或角色选项授权；否则编辑配置就可能绕过权限或把维护入口锁死。可信目标、团队和密钥引用放在部署绑定中。

GitHub Team 查询需要组织 Members read 权限。这是后台 GitHub App 的部署能力；本次匿名网页无法证明私有 Team 的具体成员，不能将网页可见性当成员判定。

## 9. PUB-01：确认页、发布事务与 Map 同步

### 9.1 发布确认页

展示当前正式配置与候选的 packageId、revision、contractRevision、完整 JSON/归档散列、基础版本，以及分类/字段/工作流/应用设置的变化摘要。身份和 Team 状态明确可见。

页面提供“再次核验”“上传并发布”“取消/关闭”。必须取得该候选的服务端独立复核结果且无强制阻断，上传按钮才启用；警告展示并按既有规则要求确认。候选修改、版本竞争、来源消失或权限过期后重新核验。

核验范围包括整包原生结构、模块语义、字段/绑定/公式引用与类型、分类树、公共表、完整性、版本及当前目标运行时支持能力。浏览器传来的 validation-report.json 是参考，不能代替服务端实际执行。

### 9.2 复用现有 pipeline 能力

优先扩展既有 ConfigPackages 的不可变归档、版本比较、授权记录、锁和活动指针机制，增加网页提交入口及 Map 配置镜像步骤；不平行维护两套活动配置权威。

将前端与 Node 端的验证核心复用/打包为无浏览器依赖的相同版本。服务端必须真正识别 r11 的字段、对照、继承、工作流绘制、条件公式、application 和原生几何能力；不能仅把 contractRevision===3 改成接受 11。

归档验证沿用当前已完成的原始字节 SHA、byteLength、声明目录与身份检查；文件/压缩包 64 MiB、累计解压 128 MiB、单条目 64 MiB、512 条目及 JSON 深度 64 的预算继续执行，既有 21 类归档负例纳入服务端回归。

服务器保留既有可信授权记录和 Control 合入验证。用户 Maintainers 确认产生受控发布事务，由 pipeline 在部署策略允许的机器写入范围执行，不伪造历史人工授权、不绕过现有批准记录。

前端大归档复用短期、限定目标的上传授权与大小/摘要检查；队列任务读取完整归档。不要把大 JSON 和最终发布都塞在一次短请求内完成。

### 9.3 历史与统一活动指针

发布保存不可变配置 JSON、完整归档、manifest、核验报告、操作者、时间、基础版本和任务 ID；旧正式版本及原始字节永久可追溯。Map 侧也保存相同的版本历史和当前入口文件。

正式活动身份至少包括 packageId、contractRevision、revision、configSha256、manifestSha256 和发布 ID；不能仅用可碰撞的 revision 判断相同内容。

**Map Git 提交、部署和 COS/SCF 写入不能假装是一个跨系统数据库事务。** 采用准备与切换流程：

1. 校验权限、基线及候选，创建幂等发布任务，锁定本次最终内容。
2. 写不可变新配置和历史归档；旧活动版本仍有效。
3. 推送 Map 配置专用路径，等待相应不可变配置在目标部署可读取，并校验字节摘要。Git 推送成功不等于部署完成。
4. 所有必需准备完成后，以预期旧指针进行条件切换，发布唯一新的正式活动指针。
5. Map 与 SCF 新任务读取这个共同的正式版本身份；配置镜像上的 current 文件仅在与该身份匹配时使用，不把尚未激活的候选当正式版本。
6. 补齐发布完成回执及 Map 当前入口镜像，显示阶段、失败原因与可重试状态。

主地图通过轻量公开索引/代理读取共同活动身份，不加载配置编辑分包。Map 本地静态副本可作字节匹配镜像与可信恢复来源；不能在未核实激活状态时选用一份抢先部署的新候选。

准备失败、Map 部署失败或基线已变：不切活动指针。切换后的回执/镜像补齐失败：保留真实已激活状态并重试补齐，不能只显示笼统失败而让用户重复发布。需要回退时创建有审计的回退事务，不删除或覆盖历史。

### 9.4 Map 写入限制

后续单次配置发布只允许更新约定的配置 JSON、manifest/活动入口和配置历史目录；不得由上传内容指定仓库、分支、任意文件路径、工作流或应用代码。不会重新覆盖 V1 兼容包、修改业务代码或重发正式数据与媒体。

本轮首次改造当然需要主应用/API/pipeline 代码更新；“仅更新配置文件”指改造完成后的日常发布事务。首次部署需确认机器账号、仓库规则与分支保护允许该受控自动流程，不以绕过保护实现自动化。

## 10. SCF-01：正式数据核验与任务版本一致

执行前查明实际 pipeline 仓库分支、SCF alias/部署版本和活动配置存储，确认现有配置导入与审核使用路径。旧本地快照只作为迁移证据，不冒充线上现状。

新建上传核验、预检、保存、批准/发布等任务，在开始时解析并记录正式活动配置引用。其余阶段按明确版本语义工作：

| 场景 | 版本处理 |
| --- | --- |
| 新创建任务 | 使用当时正式活动配置并记录完整引用。 |
| 已开始、仍在执行的任务 | 固定原引用，不在两步中间悄悄切换。 |
| 对旧包发起新的核验 | 可以按最新正式配置重新核验，生成新报告，保留旧报告。 |
| 使用旧报告确认关键状态变更 | 若要求当前基线而活动版本已变，阻断并要求重新核验；不静默复用旧通过结果。 |
| 历史任务/已发布数据查看 | 使用记录的配置/规则版本追溯，不重写历史证据。 |

分类合法性、字段值类型、嵌套路径、主附属关系和几何/多部件校验从正式 V3 上下文读取。不能前端用 V3，SCF 仍独立读取旧 Class/worlds.json 形成不同结论。

旧任务确需 V1 resolver 时按已记录的旧配置身份走隔离兼容分支；新任务不自动回退旧验证器。媒体/Relay 文件协议保留，配置版本通过执行上下文或明确版本化元数据携带，不擅自塞入现有严格协议的未知属性。

首次 r11/r7 转正前，将当前正式发布数据做只读兼容核验；发现实际不能读取/定位/编辑的问题先解决或形成明确迁移，不通过批量改写源数据掩盖。validateExistingData 的可选追溯规则保持原意，不能把原本允许的历史数据全面改判为非法。

审核自动化的环境启用条件与配置发布权限分别登记；配置转正不等于无条件打开所有审核生产操作。

## 11. PART-01：多部件与内洞的准确行为

### 11.1 界面规则

测绘页原“多部件要素”按钮统一更名为 **“多部件和内洞设置”**，桌面、移动、完整测绘及工作流相关入口一致。面板可正常打开，不因分类禁止多部件就禁掉整个入口。

| 条件 | 部件下拉框 | 部件 + | 部件 − | 面的内洞设置 |
| --- | --- | --- | --- | --- |
| 分类与当前绘制都允许多部件 | 沿用正常操作 | 可添加 | 满足现有最少一部件规则时可删除 | 正常。 |
| 分类 allowMultipleParts=false | 禁用 | 禁用 | 禁用 | 正常，不受单部件许可影响。 |
| 当前绘制页进一步限制 single | 禁止额外部件与相关切换 | 禁用 | 按当前单部件约束锁定 | Polygon 内洞仍可正常使用。 |
| 现有编号显示/控制点会话等编辑锁 | 沿用已有锁 | 沿用已有锁 | 沿用已有锁 | 仍遵守这些真实编辑锁，不取消忙碌保护。 |
| 尚未能确定当前分类 | 不新增额外部件 | 禁用并说明 | 不改变未确认结构 | 已知为 Polygon 时可保留合法单面内洞操作。 |

Point/LineString 不显示面内洞功能。Polygon 的“一个外部件 + 多个环”仍是单部件，不能把孔环数量算成部件数量。

### 11.2 许可来源与实现位置

按当前正在绘制/编辑的实际分类及几何，通过 resolveGeometryProfile 读取继承后的 allowMultipleParts。工作流使用对应输出的实际分类选择；多个输出逐页判断，不能因另一个无关输出禁止多部件就禁整条工作流。

同一次捕获若用于多个真实输出，其部件数必须满足所有相关输出约束。额外绘制使用自身返回格式和绑定目标约束；pointObject 必须单点。

拆开“部件结构锁”和“内洞结构锁”：分类单部件限制仅加入前者。选择/添加/删除部件的处理函数也检查许可，手工数组、粘贴、恢复和捕获路径不能绕过；内洞增删/选择及当前环的控制点操作继续正常。

V3WorkflowRunner 当前把添加部件与孔环放在同一个 multiple 条件下，本轮需要分开。NativeDrawingSession、通用绘制面板与最终保存共同保持结构，不仅是按钮变灰。

配置或最终分类切换后立即重算许可；已有草稿不静默截为一个部件。若已含多部件却转入禁止分类，保留草稿并报冲突/阻断保存，允许回到合法分类或调整规则后处理；按本次要求不额外开放减号作为例外。

打开/收起设置、返回信息页、切换绘制页或撤销重做均不得丢失内洞。最终分类与绘制页的单部件校验继续兜底，并补齐普通编辑和对应后端校验。

此项属于正式 V3 测绘更新，不回写已冻结 V1 兼容分包，避免违背 V1 独立保留要求。

## 13. 执行顺序与交付

1. **基线固定**：归档当前 V1 完整兼容快照、r11/r7 与正式数据只读兼容结果；核实最新 pipeline 和部署目标。
2. **核心边界改造**：分离正式/本地提供者，接线主地图；独立 V1 页面及配置编辑分包，处理旧地址。
3. **工作台与绘制**：全局核验门、自动修订、转正文案及本地导入；完成 PART-01。
4. **服务端链路**：共享 r11 验证核心，新增维护者重新登录及发布能力，扩展已有 pipeline/SCF 配置上下文。
5. **事务与镜像**：历史、幂等、锁、Map 配置专用推送、部署确认、共同活动指针与恢复机制。
6. **联合验证**：本地自动化和视觉检查 → staging 只读/干跑 → 目标环境受控端到端演练；通过后完成正式切换。
7. **交付归档**：转正执行报告、部署/配置引用、V1 冻结清单、测试证据、人工验收步骤与更新后的 JSON 阅读手册。原手册与 r11/r7 副本保留。

执行范围涉及前端仓库、现有可信 API、pipeline 源码/SCF 与 Map 配置镜像写入。首次实施前核实实际仓库、目标分支、应用安装权限、部署 alias 和恢复路径；不把过时本地 pipeline 快照直接覆盖到线上。

本轮蓝图不包含把该下游完整应用再次覆盖上游；后续若同步上游，仍按原先的空接口/本地化模板标准另行处理。

## 14. 官方依据与实现解释

- [GitHub Team membership API](https://docs.github.com/en/rest/teams/members#get-team-membership-for-a-user)：服务端可查询成员状态，GitHub App 需要组织 Members read 权限。
- [GitHub OAuth web flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)：state 关联回调、逐次确认用户身份；prompt=select_account 可请求账户选择。
- [GitHub Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)：如涉及 Actions，按发布目标分组避免同目标任务交错；不能用它替代跨 COS/Git/部署的版本锁和条件切换。

具体的“服务端短期发布凭证、共同活动指针与准备后切换”是依据当前项目发布需求作出的设计选择，不声称是 GitHub 提供的跨系统原子事务。
