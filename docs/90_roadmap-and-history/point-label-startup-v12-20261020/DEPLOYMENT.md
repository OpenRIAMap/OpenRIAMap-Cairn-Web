# r12 能力部署与验收顺序

本轮只生成代码、包和 PR；没有部署 SCF、切换别名、上传 COS 或发布配置。正式基线仍是 r9/契约 r11。

1. 先审查 Pipeline PR，部署本轮的 cairn-pipeline-worker.zip 和 cairn-pipeline-dispatcher.zip，发布新版本并将当前调用的 staging 别名绑定到新版本。沿用既有角色、触发器、资源限额、域名和生产绑定；不要复制一个假定版本号。四函数标准构建均通过，但另外两个函数未改业务行为，本轮不要求重复部署。
2. 保持当前已启用的 CAIRN_CONFIGURATION_RUNTIME_ENABLED / CAIRN_CONFIGURATION_PUBLICATION_ENABLED、真实 CAIRN_CONFIGURATION_ACTIVATED_AT 和现有生产来源域名值；本轮无新增环境变量、CAM路径或桶CORS需求，不要重新填 false/null 或改变生效时间。
3. 再合并 Web PR 并等待 Vercel 生产部署完成。现有正式 r9/契约 r11 可继续正常使用；静态图库随 Web 发布。普通启动不应请求 /api/configuration。此阶段仅增加兼容r11/r12能力，不自动切换正式配置。
4. 在配置工作台导入审查候选 ZIP，或对顶部显示的本地编辑配置执行“迁移到r12草稿”。导入或迁移均先建立整包候选，可跨三个设计标签检查；各区域保存只暂存候选，最后使用设计标签下方的整包核验、保存、放弃入口提交或取消。迁移按钮不会自动获取最新正式配置；若本地编辑内容与正式基线不同，应导入从最新正式基线生成的候选再继续。本轮默认r7与注册正式r9已逐字段比较，仅revision不同，功能内容一致，可以直接迁移。候选来源是本轮核对的注册r9；若期间正式配置又有编辑发布，应从最新正式基线重新迁移，不能直接覆盖较新内容。
5. 使用既有整包下载/上传流程：全局核验→重新登录→维护者权限→候选确认核验→上传并发布。服务端自动分配下一修订号，不保证一定叫r10；契约版本为12。既有鲜活身份绑定、active基线检查、审核推送结构保持。
6. 等待任务从 queued / awaiting-deployment 进入 active；确认 Vercel 配置镜像部署完成，再对比 Web静态身份与SCF active的包/项目/修订/契约/JSON摘要/manifest摘要/release。不要在 awaiting-deployment 阶段反复发起同一候选发布。
7. 刷新地图，检查世界/数据来源、图层按钮、图标及坏图回退、中英贴线、自定义胶囊和验证器行预览。旧缓存可先展示并提示新版本就绪，完成当前编辑后刷新切换。审核模块打开与中继包上传会即时检查SCF/Web；不一致仅阻断对应业务。
8. 用户实际执行一次登录和上传预检，以及已有审核流程的受控测试。本轮自动验收没有向正式数据提交或发布中继包。采集配置版本不同本身不拒绝包，实际数据仍按远端当前核验上下文检查。

## 包与回滚边界

SCF附件根目录 handler、依赖与共享内核已核验，摘要见 manifest.json。源码仓库 vendor/configuration-r11 是兼容旧路径名，实际 rulesVersion 为 cairnmap-r12-production-1，支持正式r11和r12。

业务已有任务中的已知r11规则引用可由新核验器继续处理，未知规则版本仍拒绝；发布确认旧报告不能跨内核更新冒充本次新核验。

尚未发布r12配置时可按原代码回退。发布r12后，不要只回退到不支持r12的旧Web/SCF；应先按既有历史配置恢复流程恢复兼容基线，再协调代码。保留现有不可变配置历史与指针切换机制。
