# V3.2 正式替换前全量核验报告

核验日期：2026-10-16。产品基线提交：`955030f`。本轮只新增检查脚本和证据，不修改编辑器、运行时、默认配置或交付 ZIP，也不执行正式替换、远端推送或线上数据写入。

## 结论

**当前默认配置具备继续预发布验收的基础，但不建议立即正式全量替换。** V1 功能配置覆盖、当前包的合法性和已有历史整包兼容检查通过；核验器新增反例测试存在漏检，应先补齐关键阻断，再执行一次同样的回归检查。

| 任务目标 | 结论 | 本轮证据 |
| --- | --- | --- |
| 覆盖 V1 原有外挂功能配置，配置可独立应用 | 在本报告定义的前端配置范围内通过；未发现未经批准的配置缺项 | 76 份原有 JSON 来源清单、16 个 Class、95 个分类路径、20 个原有执行流程；98 个普通信息卡基线场景；总体规则语义比对 |
| 模块与总包核验能够拦截冲突 | **未完全通过** | 71 个配置场景：67 个预期应阻断，实际阻断 58 个、漏检 9 个；另有 1 个警告和 3 个合法场景符合现行设计 |
| 可作为未来版本可读、可编辑的初始版本 | 当前契约和已有迁移机制具备基础，未来兼容仍需制度化保障 | r8/r9/r10/r11 历史整包读取、迁移、ZIP 往返通过；旧分类树单独导入有特定限制，见后文 |
| 大量配置/版本的保存与读取 | 当前规模通过，长期历史列表需要优化 | 495 节点合成包往返通过；独立浏览器 25 份历史版本列表读取约 6 秒 |

本轮未把“现有测试全绿”解释为“所有可能配置都正确”。现有 57 套配置测试及生产构建通过，原 V1 的 6 项来源核验也通过；新增反例检查才揭示下述缺口。

### 1.3 文件结构与加载

ZIP 为完整快照，包含 `config.json`、manifest 和校验/来源/应用依赖报告。字段、节点、工作流和对照表用稳定标识引用；历史版本按包 ID/revision 保留，已有同版本不同内容不能覆盖；活动配置会在启用前重新核验并编译缓存。

不要求把大量独立配置同时加载进运行时：当前活动包与历史列表是两条读取路径。不过历史列表确实存在全量读取问题，见第 4 节。ZIP 读取的完整性检查也尚不充分，不能据此保证任意规模、任意文件内容都能安全而流畅地加载。

## 2. 核验入口及反例结果

### 2.1 实际入口

| 入口 | 实际边界 |
| --- | --- |
| 分类草稿核验与正常保存 | 合并后的整包 `validateConfigPackage`，包含受影响工作流及信息卡 |
| 工作流“核验” | 当前工作流 `validateWorkflowDefinition`；保存时再核验整包 |
| 公共对照表核验/保存 | `LookupTablesWorkspace` 合并表格草稿后核验整包，不只调用表格子检查函数 |
| 总体规则各模块保存 | 合并草稿后核验整包，涉及身份变更还显示影响确认 |
| Class 树内保存 | 保存到暂存树，不等于注入主配置；外层保存再进行整包检查 |
| 总包导出 | 重新计算核验结果，传入旧的“已通过”报告不能绕过 |
| 运行启用与持久保存 | `prepareConfigForActivation` 再核验，再编译 |

这些入口共享大量检查。因此共享检查漏掉的问题，通常也会穿过模块核验、整包导出和启用。本轮 9 个配置漏检场景均可通过总包核验、导出和启用；不能认为最后一步一定能补住。

### 2.3 确认的 9 个配置漏检场景

| 场景 ID | 问题及实际影响 | 优先级与建议 |
| --- | --- | --- |
| WF18 | 同一输出字段存在两条无条件组装，核验仍通过；后写入值覆盖前写入值。两者类型都合法时，提交类型检查也无法发现意图冲突 | **P1**：建立目标写入索引，阻断重复无条件写入；条件写入需检查可重叠性，或明确声明覆盖顺序 |
| WF19、WF20 | 关闭编辑用途后，`Level` 的表达式写成 `"not-a-number"` 或 `join("",A)`，仍通过模块、整包、导出和启用 | **P1**：补充 AST 常量及已知函数返回类型推断。明确类型不兼容时阻断；无法静态确定时给诊断并提供试运行，不把所有动态表达式一律拒绝 |
| FD05 | 同一节点两个不同 key 可以使用同一个 fieldId。实测选择 `AuditValue` 后，该引用会解析到 `Name` | **P1**：在有效字段作用域检查稳定 ID 唯一性，处理继承同一字段的合法引用，不只检查 key |
| CD03 | 同一信息卡中条目 ID 可重复；编辑器按 ID 更新时会同时命中多个条目 | **P1**：信息卡保存前校验条目 ID 唯一性，导入/模板复制也执行相同检查 |
| RD12 | `not-a-color` 这样的固定颜色可通过核验，浏览器 `CSS.supports` 实测为 false | P2：使用共享的颜色语法校验，合法 CSS 颜色与非法值明确区分，不能只检查非空字符串 |
| RD13 | 几何动态优先级可引用不存在的 `MissingWeight`；相近的 Label 碰撞指标已有存在性检查，这里未对齐 | P2：核对字段存在性、单值/多值及数值能力，采用与 Label 一致的检查 |
| CT04、CT05 | children 可以指向其他 Class，或遗漏真实子分类，只要被指节点存在就可通过 | P2：以连续 path 作为单一分类树依据，生成 children 并检查双向一致，避免两份树结构逐渐分歧 |

表达式错误有运行时兜底：实测组装记录中的 `Level="not-a-number"` 会得到“Level 必须是有限数值”，原生提交入口会拒绝写入。这可以保护要素数据，但**不能替代配置输出前的阻断**，否则会保存并分发一个无法完成采集的流程。

以上是 9 个失败场景，按共同原因归纳为 7 组问题，不代表只有 7 种错误输入。

### 2.4 需要区分的合法行为

- r11 允许不同渲染条件/Zoom 范围重叠，并按规则顺序覆盖。完整条件重复会报错；后规则无条件完全遮蔽前规则只给 `render-match-shadowed` 警告；部分交叠可以合法通过。不能把所有重叠都当成冲突，否则会破坏既有默认规则。建议增加规则命中轨迹/遮蔽分析，明确哪些重叠是作者有意安排。
- `tags.*` / `extensions.*` 保留动态扩展路径能力。删除同名可选字段定义，不必然使该路径的 assignment 变成非法。建议对“过去明确声明、后来删除”的依赖给专门警告，而不是禁止所有未声明扩展路径。
- 数值控件的默认值 `"12"` 可被规范化为数值，属于现行兼容行为；本轮没有把它计为类型漏检。

### 2.5 已挂载数据的额外边界

当前 `validateExistingData` 主要用于显式开启的必填检查及结构关系检查，并非全量历史数据类型迁移器。本轮额外检查了嵌套必填字段、嵌套条件和已有数值字段的错误类型，结果详见机器摘要的 `mountedAudit`：

1. 已有 `tags.nomenclator` 的嵌套值存在时，现有必填检查仍按 `record['tags.nomenclator']` 查找，可能误报缺失。
2. 条件引用 `tags.flag` 时，同样的扁平读取可能漏掉满足条件后应执行的必填检查。
3. 已有记录 `Level` 的错误类型不会仅因开启该标记就被全面检查。

建议将嵌套读取统一为 `readRecordPath`，并另外提供“已有数据影响审计”模式。不要突然把所有历史记录强制套用新 schema；默认的兼容策略和显式审计开关应保留。这部分不影响当前未开启相关检查的默认包，但不宜宣称编辑器已经完成真实数据的全量迁移验证。

这说明当前 r11 可以作为一个明确的初始基线保存和再编辑。旧包在内存副本上迁移，原始文件没有被改写；当前包的结构和本地历史机制也能保留版本身份。

**单分类/分类树文件的旧版兼容与整包兼容不是同一件事：**

- r8 不支持直接导出后来的分类树格式，需要先升级整包。
- 未升级的 r9 `FLR` / `STF` Class 树直接进入 r11 时，旧 visibility/context 与新结构角色契约冲突；即使选择现有“修正上游冲突”也不能通过。先将 r9 整包升级为 r11，再导出这些树，16 棵全部通过。
- 建议补充分类树文件自身的版本迁移链，或在导入时准确提示“先升级整包再导出”，不要只给一般性字段冲突说明。

本轮历史文件实测覆盖 r8–r11。更早 r3/r4/r5 的入口和迁移仍有现有单测，但没有据此声称任意早期个人文件均已完成实测。

### 3.2 对未来版本的要求

未来版本尚未存在，当前检查无法证明未来代码一定兼容。应把下面事项固定为后续升级的硬性回归门：

1. 冻结当前 r11 JSON/ZIP 的 schema、SHA 和来源，不用修改这份历史文件来“修复”将来的兼容测试。
2. 新契约新增显式、可复跑的迁移步骤；保留旧读入口，不用“用最新版默认值重建”替代用户原配置。
3. 同时测试总包、分类树、单分类、工作流和对照表依赖；迁移后再次导出、重读、编译及运行关键场景。
4. 未知的更高契约继续拒绝启用；允许保留原文件供检查，而不是静默丢弃不认识的设置。
5. 原始副本、迁移副本和活动配置分开显示；后续可增加迁移前后差异视图。当前没有专门的完整双版本可视化 diff，本轮比较通过脚本完成。

按上述约束持续维护，才可以把“未来可检查、比较、编辑初始版本”变成稳定承诺。仅保留一个 `schemaVersion` 字段并不足够。

### 4.1 单包规模实测

以下为本机 Node 24 单次测量，使用当前包加同构新 Class 根节点；时间有运行波动，不能当作低配设备性能承诺。ZIP 重复内容很多，压缩率不能外推到任意项目。

| 分类节点 | 紧凑 JSON | 整包核验 | 编译 | 重新核验并导出 ZIP | ZIP 读取 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 95 | 约 1.55 MiB | 约 0.16 秒 | 约 0.03 秒 | 约 0.22 秒 | 约 0.03 秒 |
| 195 | 约 3.87 MiB | 约 0.35 秒 | 约 0.07 秒 | 约 0.51 秒 | 约 0.08 秒 |

### 4.2 历史列表

独立 headless Edge 配置目录中，使用实际 `configLabStorage` 和完整历史快照测得：

| 历史版本数 | 列出并核验全部历史 | 单条 latest 原文读取 |
| --- | ---: | ---: |
| 1 | 约 0.30 秒 | 约 25 ms |
| 10 | 约 2.54 秒 | 约 19 ms |
| 25 | 约 6.02 秒 | 约 18 ms |

原因是 `listConfigLabPackages` 逐条读取并执行 `prepareConfigForActivation`，还保留全部已编译包对象。Config Lab 进入 V3 和刷新版本列表时会调用它。**这是真实的历史管理扩展性问题，不是 ZIP 无法表达大量配置。**

建议另存历史摘要并分页，列表只读 ID、版本、名称、时间、摘要和核验状态；用户选中版本后再加载并核验一个包。摘要和完整历史应在同一事务更新，继续保留现有不可变历史保护。必要时增加存储占用提示和主动归档，不自动删除用户历史。

### 4.3 ZIP 完整性检查缺口

当前篡改 `config.json` 会被哈希检查拒绝，但以下 4 种情况仍能读入：报告文件被改动、未知 manifest schema、manifest 包身份与 config 不一致、错误的 byteLength。

这些结果**不表示无效配置可以绕过语义校验**；导出和启用仍会重新检查配置，也没有把导入报告当成授权凭证。但归档的“所有文件完整性”承诺不充分。建议严格校验 manifest schema、包身份、所有声明文件的 hash/长度，补充条目数和压缩/解压体积限额及清楚的超限提示。

## 5. 建议的正式替换前处理顺序

1. **先修 P1**：重复写入目标、已知表达式类型冲突、fieldId 和信息卡条目 ID 唯一性。将对应反例改为必须通过的 CI 阻断测试，再回归现有默认包。
2. **补齐配置一致性**：动态优先级字段、颜色、分类 children/path 一致性；补充旧 Class 树的迁移提示或转换；修正已挂载数据的嵌套读取。
3. **处理版本积累**：历史摘要/分页/按需核验，避免配置编辑次数增加后出现数秒卡顿。
4. **固定初始版本兼容门**：保存当前 r11 冻结样本，未来每次契约升级同时运行整包及各类分文件回归；完善 ZIP manifest 和文件规模检查。
5. 使用真实项目数据完成一次最终切换演练，包含图层、搜索、标准/外部采集、编辑回填和旧配置恢复，再决定正式替换。

本轮没有修改上述产品行为，避免把审计结果与未经确认的修复混在一起。默认包本身通过核验；阻止直接给出“完全就绪”的原因，是已经实测的核验漏检和扩展性边界。
