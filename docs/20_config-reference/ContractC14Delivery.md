# c14 契约迁移、Halo 与编辑折叠交付说明

本轮配置修订继续使用 `rN`，契约展示改为 `cN`。JSON 中的 `revision`、`contractRevision` 仍为数字；历史协议名、文件名和核验规则身份继续兼容，不做字符串批量改名。

## 功能与边界

- c13 → c14 的相邻迁移同时支持完整包、单分类、Class 树和工作流。目标只支持当前版本及此前五版，最低 c13；每跳检查结构。完整包复用组件转换，保留用户值、ID、顺序和配置修订，不逐跳增加 r。
- 组件导入到当前工作稿契约；完整包导入 c13+ 默认生成当前最新契约的隔离候选。继续编辑缓存、读取分类、重复读取已打开草稿和普通区域保存保持来源契约。c12 及更早组件先经完整包历史桥接到 c13，再重新导出。
- 当前导入原件、原件摘要、迁移结果摘要和分组提示保存在单份工作区附件。提示可定位、按组清除和全清；清除不改变配置、不代替核验。原件可下载。临时诊断包可携带迁移报告，正式包不携带诊断附件。
- 完整基础点、图标、每个图片定义／映射行、图标／图片回退点及线面几何增加 Halo。迁移默认关闭，初始 2 CSS px／白色，范围 0～72。颜色复用通用五种模式及映射行预览、外部引用资格和回退。
- 图片 Halo 沿配置宽高的矩形外缘，不读取透明像素。图标沿底板或图案路径合成，增加画布时补偿锚点，原图案不放大。回退点独立，失败资源不残留图片矩形。
- 几何 Halo 复用 Leaflet SVG 投影路径，增加一个无事件目标的底层 SVG path；不增加业务要素，不重建导航或搜索索引。当前正式渲染使用 SVG，本轮未新增 Canvas 渲染后端。
- 字段、信息卡和渲染规则首次全部折叠；新建条目自动展开，缓存恢复使用页面／分类和稳定条目 ID。旧序号偏好不套用到新条目，业务草稿保留。整包候选内尚未保存的分类草稿也能恢复。
- 原有线点化运行分支在原生编辑器补齐“线中点”选项，与面中点共用点符号及独立 Halo。既有普通线规则保持原表示。

旧 `conditionalOverrides` 在 c7+ 仍按既有语义门禁拒绝；本轮保留诊断来源而不静默删除。正式条件使用 `when.fields`，不会借迁移重新启用已禁用的旧条件协议。

## 已完成验证

- `npm run verify:ci`：包含历史契约与发布回归、正式镜像、CLI、业务一致性、临时包、文案／能力维护检查及 c14 迁移矩阵。
- c14 夹具冻结在 `scripts/config-tools/fixtures/c13-baseline.config.json.gz`，不依赖未来可变的 `public/configuration/current.json`。覆盖 95 个单分类、16 棵 Class 树、28 个工作流、组件与完整包等价、防降级／未知契约、模拟未来五版窗口、源未变和新建 Point／LineString／Polygon 默认值。
- `npm run build`：离线生成物检查、TypeScript、Vite 及冻结 V1 安装。完整浏览器与迁移矩阵放在 PR CI，生产 build 不联络 SCF／COS／GitHub。
- `studio_workspace_acceptance.py`：真实本机浏览器完成缓存选择、临时包导出／导入／修复／正式导出、配额和页面生命周期等既有工作流。
- `c14_acceptance.py`：实际文件选择和分类／树／工作流导入保存、标准 ZIP 原件下载字节比对、迁移提示、默认折叠、五色控件／映射样例、图标两页弹窗、全部基础点形状／点集合、图片四来源／映射行／失败回退、线面及点化切换、缓存继续编辑、保存基线与当前候选契约不同的迁移。
- `c14_render_acceptance.py`：实际 SVG／DOM 检查虚线相位、线端／转角、缩放更新、透明面内洞／多部件、0／移除／重加清理、自定义图片锚点、高 DPI、图标合成缓存与 600 路径对比。
- Pipeline：202 项测试通过，含 c14 正式归档／发布、非法 Halo／未来契约拒绝及 c11／c12／c13 历史核验规则和在途快照。SCF 部署配置和根入口验包通过。Web／Pipeline 随包核验器及其 manifest 字节一致。

本机浏览器使用独立 Chrome 配置目录并阻断外部网络／业务 API，没有执行真实登录、COS 上传或正式发布。外部取色在样例中验证配置与回退；真实关联目标、远端图片网络失败和正式数据密度仍需部署后验收。未声称已完成 Firefox／移动设备的全面回归。

600 条本机合成线的三次测试：业务图层始终 600，Halo 关闭／开启 SVG path 为 600／1200；开启创建耗时约 19～25ms，关闭约 15～18ms。帧对齐和设备噪声使单次平移时间不能当作性能提升；该结果不等于真实整图性能保证。测试记录设备、DPR 1／2 和浏览器堆快照，不把未强制 GC 的堆数值作为泄漏结论。

## 部署顺序

1. 审查 Web 与 Pipeline 两个 PR。先部署本轮 **pipeline worker、dispatcher** ZIP，分别发布新版本并绑定现有 `staging` 别名。保留现有域名环境值、功能开关和激活时间；没有新增环境变量、CAM 或 CORS 要求。
2. archive worker 和 github mirror worker 本轮无需部署：其运行工厂不调用配置业务服务。打包脚本仍可生成四个包，部署清单仅要求前两个。
3. 合并／部署支持 c13 和 c14 的 Web。普通地图继续读取既有正式 c13；本轮没有改动 `public/configuration`、冻结默认配置或 V1 发布资源。
4. 在工作台明确恢复当前正式配置；如果有缓存，先选择继续编辑并处理草稿，或明确恢复默认。点击“迁移到 c14 草稿”，或导入本轮审查候选 ZIP。候选携带原配置修订 r11，契约 c14；正式发布的下一修订由服务器分配。
5. 查看迁移提示：默认 80 个 Halo 设置关闭、1 条身份转换。跨三个设计标签编辑时，区域核验保存只暂存到候选；之后顶部核验／保存整包。不得修改 `contractRevision` 数字冒充完成迁移。
6. 使用全局核验和既有登录／上传发布入口。等待镜像及对应 Vercel 部署完成，确认正式配置身份、工作台身份和 SCF 业务一致性检查均通过。
7. 使用实际 Firefox／目标设备检查少量开启 Halo 的图标、透明图片、点集合、线面、取色关系、点击和图层开关；再做真实中继包上传预检、审核预检和发布确认回归。

c14 激活前可保留 c13 正式指针回退。c14 已激活后，不可只回滚到不识别 c14 的旧 Web／SCF；应按现有配置发布恢复机制协调前后端与正式指针。
